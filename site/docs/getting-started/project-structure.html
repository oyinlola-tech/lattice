PROJECT STRUCTURE

Understand the standard Zudo project layout and conventions.

Guide Conventions Monorepo

Single Project Layout

A standard Zudo application follows this directory structure:

my-zudo-app/
├── src/
│   ├── config/
│   │   └── index.ts              # App configuration
│   ├── modules/
│   │   ├── auth/
│   │   │   ├── index.ts          # Module barrel
│   │   │   ├── auth.service.ts   # Service implementation
│   │   │   └── auth.type.ts      # Types & interfaces
│   │   └── users/
│   │       ├── index.ts
│   │       ├── users.service.ts
│   │       ├── users.repository.ts
│   │       └── users.type.ts
│   ├── errors/
│   │   └── index.ts              # Custom error classes
│   └── index.ts                  # Application entry point
├── tests/
│   ├── unit/
│   │   └── auth.test.ts
│   └── integration/
│       └── users.test.ts
├── dist/                         # Compiled output
├── package.json
├── tsconfig.json
└── zudo.config.ts                # Zudo configuration

Directory Breakdown

src/

The source directory contains all application code. All TypeScript source files live here.

  • • Entry point: src/index.ts
  • • Compiled to: dist/
  • • Never import from dist/ — always use src/
src/config/

Application configuration module. Exports typed config objects used throughout the app.

// src/config/index.ts import { defineConfig } from "@zudojs/config"; export const appConfig = defineConfig({ app: { name: "my-app" }, server: { port: 3000 }, });
src/modules/

Feature modules. Each domain gets its own subfolder with services, repositories, and types.

  • • One folder per domain (auth/, users/, products/)
  • • Each folder has an index.ts barrel export
  • • Separate files for services, repositories, types, and handlers
  • • Modules register with the DI container
src/errors/

Custom error classes that extend BaseError from @zudojs/errors.

// src/errors/index.ts import { BaseError, ErrorCode } from "@zudojs/errors"; export class UserNotFoundError extends BaseError { readonly code = ErrorCode.NOT_FOUND; constructor(userId: string) { super(`User not found: ${userId}`); } }
tests/

Test files organized by type. Uses Vitest as the test framework.

  • • tests/unit/ — Unit tests (fast, isolated)
  • • tests/integration/ — Integration tests (real dependencies)
  • • Mirror the src/ directory structure
  • • Test files: *.test.ts or *.spec.ts
dist/

Compiled JavaScript output. Generated by tsc. Added to .gitignore — never commit compiled files.

Monorepo Layout

For multi-package projects, Zudo uses npm workspaces with this structure:

zudo/
├── packages/
│   ├── errors/
│   │   ├── src/
│   │   │   ├── index.ts
│   │   │   └── ...
│   │   ├── tests/
│   │   ├── package.json
│   │   └── tsconfig.json
│   ├── logger/
│   │   ├── src/
│   │   ├── tests/
│   │   ├── package.json
│   │   └── tsconfig.json
│   ├── config/
│   │   └── ...
│   └── core/
│       └── ...
├── site/                          # Documentation site
│   ├── docs/
│   ├── css/
│   ├── js/
│   └── assets/
├── tests/                         # Integration tests
├── package.json                    # Workspace root
├── tsconfig.json                   # Base TS config
└── LICENSE

WORKSPACE ROOT

The root package.json uses "workspaces": ["packages/*"] to manage all @zudojs packages from a single repository.

Dependency Flow

Packages follow a strict dependency hierarchy — lower layers never depend on higher layers:

Layer 1 — Foundation     errors, constants, types
        ↑
Layer 2 — Primitives     logger, container, crypto, config, events, middleware
        ↑
Layer 3 — Application    core, cqrs, auth, http
        ↑
Layer 4 — Platform       runtime, cli, adapters

Conventions

DO

  • • Use index.ts barrels in every folder
  • • Keep files under 150 lines
  • • Keep folders under 5 files
  • • Import from @zudojs/* packages
  • • Use import type for type-only imports
  • • Add .js extensions on relative imports
  • • Use named exports only
  • • Run typecheck before committing

DON'T

  • • Use default exports
  • • Use console.log (use @zudojs/logger)
  • • Create local error classes (use @zudojs/errors)
  • • Duplicate types from shared packages
  • • Bypass the DI container
  • • Hardcode configuration values
  • • Use any type
  • • Use var (use const/let)

IMPORTANT

Before defining a type in a new package, search all shared packages first: grep -r "type.*TypeName" packages/*/src. Types should be imported from the owning package, never redefined.
