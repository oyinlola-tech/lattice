RUNTIME

The application runtime that orchestrates startup, shutdown, and lifecycle management.

Overview

The Zudo runtime is responsible for bringing your application to life. It manages the complete lifecycle from initialization through graceful shutdown, handling signal trapping, dependency ordering, and error recovery.

The runtime uses a state machine to track the application's current phase and enforces valid transitions between states.

Lifecycle States

The runtime transitions through five states during the application lifecycle: 

  CREATED
     │
     ▼
  INITIALIZING    ← modules.resolve(), modules.initialize()
     │
     ▼
  READY           ← modules.start(), accepting requests
     │
     ▼
  SHUTTING_DOWN   ← signal received, modules.stop() in reverse order
     │
     ▼
  DISPOSED        ← modules.destroy(), all resources released
State Description Allowed Transitions
CREATEDRuntime instantiated, not yet started→ INITIALIZING
INITIALIZINGResolving dependencies, calling module.initialize()→ READY, → SHUTTING_DOWN (on error)
READYAll modules started, application accepting work→ SHUTTING_DOWN
SHUTTING_DOWNGraceful shutdown in progress, modules stopping→ DISPOSED
DISPOSEDAll resources released, runtime unusable— (terminal state)

Runtime Initialization

Creating and starting a Zudo runtime:

import { createRuntime } from "@zudolib/runtime"; const runtime = createRuntime({ modules: [ configModule, loggerModule, databaseModule, authModule, httpModule, ], config: { shutdownTimeout: 30000, // 30s grace period enableSignals: true, // Trap SIGTERM, SIGINT } }); // Start the application await runtime.start(); console.log(`Runtime state: ${runtime.state}`); // "ready"

Graceful Shutdown

The runtime automatically traps SIGTERM and SIGINT signals and initiates a graceful shutdown. Modules are stopped in reverse dependency order (the opposite of initialization order).

// Manual shutdown trigger await runtime.shutdown(); // Shutdown sequence: // 1. Transition to SHUTTING_DOWN // 2. Stop modules in reverse order // - httpModule.stop() (stops accepting connections) // - authModule.stop() (closes auth connections) // - databaseModule.stop() (drains connection pool) // - loggerModule.stop() (flushes pending logs) // - configModule.stop() (cleanup) // 3. Destroy modules in reverse order // 4. Transition to DISPOSED

SHUTDOWN TIMEOUT

If a module's stop() exceeds the configured shutdownTimeout, the runtime logs a warning and continues shutting down remaining modules. This prevents a single misbehaving module from blocking the entire shutdown process.

Signal Handling

By default, the runtime traps POSIX signals and converts them into graceful shutdown:

Signal Behavior Typical Use
SIGTERMGraceful shutdownContainer orchestration (Docker, K8s)
SIGINTGraceful shutdownCtrl+C in terminal
SIGHUPConfiguration reloadReload config without restart
// Disable automatic signal handling const runtime = createRuntime({ modules: [...], config: { enableSignals: false // Handle signals yourself } }); // Custom signal handling process.on("SIGTERM", async () => { console.log("Custom shutdown logic..."); await runtime.shutdown(); });

Error Recovery

If a module fails during initialization or startup, the runtime:

  1. Logs the error with the module name and stack trace
  2. Stops all already-initialized modules in reverse order
  3. Transitions to SHUTTING_DOWN → DISPOSED
  4. Rejects the start() promise with the original error
try { await runtime.start(); } catch (error) { console.error("Failed to start application:", error); process.exit(1); }
