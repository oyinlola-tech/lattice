DEPENDENCY DIRECTION

Strict dependency rules that prevent circular imports and maintain clean architecture.

Overview

Zudo enforces a strict dependency direction to prevent circular imports and maintain a clean, testable architecture. Dependencies always flow inward — from higher-level packages toward lower-level foundations.

This rule is enforced at build time through TypeScript project references and at development time through the depcheck tooling.

Dependency Direction Rules

Layer 1: FOUNDATION  (leaf packages — no internal deps)
  errors, constants, types

Layer 2: RUNTIME PRIMITIVES  (depend only on Layer 1)
  container, logger, events, crypto, validation,
  schema, config, middleware, serialization

Layer 3: APPLICATION  (depend on Layers 1-2)
  cqrs, messaging, queue, cache, storage, lifecycle

Layer 4: PLATFORM  (depend on Layers 1-3)
  core, runtime, http, auth, adapters, database,
  observability, security, permissions, transactions,
  tenancy, feature-flags, docs, plugins, testing

DEPENDENCY RULE:
  Layer N may ONLY depend on Layers 1 through N-1
  NEVER on the same layer or higher layers

Layer 1 — Foundation

errors, constants, types. Zero internal dependencies.

Layer 2 — Runtime

container, logger, events, crypto, validation, schema, config, middleware, serialization

Layer 3 — Application

cqrs, messaging, queue, cache, storage, lifecycle

Layer 4 — Platform

core, runtime, http, auth, adapters, database, observability, security, etc.

Package Dependency Graph

The dependency graph flows strictly downward. Here are representative connections: 

@zudolib/http
  ├── @zudolib/core
  ├── @zudolib/errors
  ├── @zudolib/logger
  └── @zudolib/security

@zudolib/runtime
  ├── @zudolib/errors
  ├── @zudolib/constants
  ├── @zudolib/container
  ├── @zudolib/config
  ├── @zudolib/logger
  ├── @zudolib/events
  └── @zudolib/core

@zudolib/auth
  ├── @zudolib/errors
  ├── @zudolib/constants
  └── @zudolib/permissions

@zudolib/adapters
  ├── @zudolib/errors
  ├── @zudolib/constants
  ├── @zudolib/types
  └── @zudolib/lifecycle

Foundation (Layer 1):
  errors ← no dependencies
  constants ← errors
  types ← no dependencies

Allowed and Forbidden Import Patterns

ALLOWED

✓ @zudolib/http → @zudolib/errors
✓ @zudolib/http → @zudolib/logger
✓ @zudolib/cache → @zudolib/errors
✓ @zudolib/cache → @zudolib/types
✓ @zudolib/runtime → @zudolib/container
✓ @zudolib/logger → @zudolib/errors
✓ @zudolib/events → @zudolib/constants

FORBIDDEN

✗ @zudolib/errors → @zudolib/logger
✗ @zudolib/types → @zudolib/errors
✗ @zudolib/logger → @zudolib/config
✗ @zudolib/events → @zudolib/middleware
✗ @zudolib/cache → @zudolib/logger
✗ @zudolib/container → @zudolib/core
✗ Any circular dependency

CRITICAL RULE

If Package A imports from Package B, then Package B must NOT import from Package A. Circular dependencies at the package level are always a design error that must be fixed.

How to Verify Dependency Direction

Manual Check

// Check what a package imports grep "from '@zudolib/" packages/http/src/**/*.ts // Check for circular dependencies npx madge --circular packages/*/src/index.ts

Automated Enforcement

// In tsconfig.json — TypeScript project references { "references": [ { "path": "../errors" }, { "path": "../constants" } ] } // In package.json — depcheck configuration { "depcheck": { "ignores": ["@types/*"], "detectors": ["import"] } }

CI/CD Integration

// .github/workflows/dep-check.yml - name: Check dependency direction run: | npx depcheck --quiet npx madge --circular --extensions ts src/

Why This Matters

Testability

Packages with no internal dependencies can be tested in complete isolation. Foundation packages like errors and types can be unit tested without any mocks.

Tree-Shaking

When dependencies flow one direction, bundlers can efficiently eliminate unused code. Importing @zudolib/errors won't pull in @zudolib/http.

Independent Publishing

Packages can be published and versioned independently. A breaking change in @zudolib/http doesn't force a release of @zudolib/errors.

Parallel Development

Teams can work on different layers simultaneously without merge conflicts, since lower layers don't change when upper layers are modified.
