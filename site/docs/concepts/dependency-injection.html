DEPENDENCY INJECTION

Token-based dependency injection container for loosely coupled architecture.

Overview

@zudolib/container provides a token-based DI container that manages application dependencies. Services are registered with tokens and resolved at runtime, enabling loose coupling, testability, and flexible composition.

Architecture Position

Sits in Layer 1 (Foundation). Only depends on @zudolib/errors.

Container Registration

Services are registered using tokens (strings, symbols, or class references) and providers (factories or classes).

import { createContainer, token } from "@zudolib/container"; // Define tokens const LoggerToken = token<Logger>("Logger"); const DatabaseToken = token<Database>("Database"); // Create container and register const container = createContainer(); container.register(LoggerToken, { useFactory: () => new ConsoleLogger(), }); container.register(DatabaseToken, { useClass: PostgresDatabase, });

Resolution Strategies

Strategy Description Use Case
singleton One instance shared across the entire application Database connections, loggers, config
transient New instance created on every resolution Request handlers, validators
scoped One instance per scope (e.g., per request) Repositories, services with request state
// Singleton — same instance everywhere container.register(LoggerToken, { useFactory: () => new ConsoleLogger(), lifetime: "singleton", }); // Transient — new instance each time container.register(HandlerToken, { useClass: RequestHandler, lifetime: "transient", }); // Scoped — one instance per scope container.register(RepoToken, { useFactory: (c) => new UserRepository(c.resolve(DatabaseToken)), lifetime: "scoped", });

Circular Dependency Detection

The container detects circular dependencies at resolution time and throws a clear error with the dependency chain, preventing infinite loops.

ContainerError: Circular Dependency

Token A → Token B → Token A detected. Break the cycle by introducing an interface token or restructuring.

Testing with DI

DI makes testing trivial — swap real implementations for mocks by overriding registrations in test containers.

import { createContainer, token } from "@zudolib/container"; const DatabaseToken = token<Database>("Database"); describe("UserService", () => { it("creates user", async () => { const container = createContainer(); container.register(DatabaseToken, { useFactory: () => createMockDatabase(), }); const service = new UserService(container.resolve(DatabaseToken)); const user = await service.create({ name: "Test" }); expect(user.name).toBe("Test"); }); });

Why DI Matters

  • 01 Loose coupling — services depend on interfaces, not concrete implementations.
  • 02 Testability — swap any dependency with a mock in tests.
  • 03 Lifecycle control — singletons, transients, and scoped instances managed automatically.
  • 04 Composition root — all wiring happens in one place, making architecture visible.
