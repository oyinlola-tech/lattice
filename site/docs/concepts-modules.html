Modules

Primary building blocks with explicit boundaries and dependency contracts.

MODULES BOUNDARIES CONTRACTS

Overview

Modules are the primary organizational unit in Zudo. Each module encapsulates a feature boundary — its own providers, services, routes, and lifecycle hooks. Modules declare their dependencies and are composed at the application level.

Architecture Position

Modules live in @zudojs/core and are orchestrated by @zudojs/runtime.

Module Definition

A module is defined by implementing the Module interface. It declares its name, dependencies, and a setup function.

import { Module } from "@zudojs/core"; const AuthModule: Module = { name: "auth", dependencies: ["config", "database"], async setup(container) { // Register services in the DI container container.register(AuthServiceToken, { useClass: AuthService, lifetime: "singleton", }); // Return lifecycle hooks return { async onStart() { await container.resolve(AuthServiceToken).initialize(); }, }; }, };

Module Dependencies

Modules declare their dependencies explicitly. The framework resolves the correct initialization order using topological sort.

// Dependency graph // // config ──→ database ──→ auth ──→ api // ↓ // cache ──→ api const ApiModule: Module = { name: "api", dependencies: ["auth", "cache"], // Starts AFTER auth and cache are ready };

Module Registration

Modules are registered with the application before startup. The runtime orchestrator handles initialization.

import { createApp } from "@zudojs/core"; const app = createApp({ modules: [ ConfigModule, DatabaseModule, CacheModule, AuthModule, ApiModule, ], }); await app.start(); // Modules start in dependency order // config → database → cache → auth → api

Module Lifecycle

Each module can define lifecycle hooks that run at specific points in the application lifecycle.

onStart

Runs when the application starts. Initialize connections, warm caches, start background tasks.

onStop

Runs during graceful shutdown. Drain connections, flush buffers, stop background tasks.

Best Practice

Keep modules small and focused. One module = one feature boundary. If a module exceeds 5 files, consider splitting it.

Why Modules Matter

  • 01 Feature boundaries — each module owns its domain, making the codebase navigable.
  • 02 Incremental adoption — start with one module, add more as your app grows.
  • 03 Team scaling — different teams can own different modules with clear boundaries.
  • 04 Testability — test modules in isolation by providing mock dependencies.
